# ADR-002：SQLite 元数据索引、迁移与独立验收

日期：2026-11-03。状态：已采纳，适用于本机开发验证版。执行范围为 T015；T014/G0、G1 和发布门仍未通过。

## 决定与依赖

将环境元数据从全量覆盖的 JSON 清单改为 SQLite 事务索引。该基础层不依赖尚待验证的画布、复杂 frame、身份提供方或支付沙箱，可以先在本机独立开发和验收。原计划 T015 的 T014 前置关系保留；本次工作包通过不代表 G0 评审已完成，也不授权跳过后续阶段的集成门。继续沿用开发 POC 模式，不增加商业准入或额度判断。

SQLite 3.54.1 来自官网 2026 年 amalgamation。下载包大小 2,990,966 字节，官网 SHA3-256 为 `92281c86e2957f9b9305890f9ac04204caa7b677cc868dc326d942689df28e30`；本机下载结果匹配。版本、源标识、SHA-256 与原始文件见 [依赖锁](../../third_party/dependencies.lock.json)，公共领域声明网页快照见 [copyright.html](../../third_party/sqlite/copyright.html)。仅链接未经改写的 sqlite3.c/sqlite3.h，不引入命令行 shell 或扩展。

第三方 C 源使用同一 v142 工具链和 MDd/MD 编译，单独目标使用上游适用的告警设置；自有 C++ 保持 C++14、W4/WX 和现有注释/格式/编码规范。SQLite 开启线程互斥，关闭动态扩展和双引号字符串兼容。原始上游字节及自有文件的 UTF-8 无 BOM、LF 均保留。

## 数据和提交

每个受管根目录使用 `workbench.sqlite3`，保留原有进程独占 `.owner.lock`。数据库路径及 WAL/SHM/journal 拒绝重解析点、目录和硬链接；根目录仍只接受空目录或已有受管索引。`application_id=0x41574250`、mode、user_version、连续迁移记录及 SQL SHA-256 必须匹配；执行完整性与外键检查。损坏、未知应用、未来版本或迁移记录变动均报错，不自动建立空库。

| 表/列 | 实际实现 |
| --- | --- |
| catalog_meta | mode 和一次性 legacy_import 标志 |
| schema_migrations | 连续版本号和固定迁移 SQL SHA-256 |
| profiles | 不透明 32 位十六进制 ID、Unicode 名称、可选实验 HTTP 代理 |
| profile_origins | Profile 外键、顺序、规范化 HTTP(S) 来源；来源不重复 |
| v2 扩展列 | revision=1、created_at、updated_at；既有 v1 创建时间未知时明确保留 unknown-legacy |

revision 目前是存储准备字段；没有借此宣称已完成配置更新、乐观锁或回收站。流程、任务、证据、授权等未来模型不建立空表冒充实现。

数据库使用 WAL、synchronous=FULL、每 1000 页自动检查点。单连接互斥串行化；写操作使用 BEGIN IMMEDIATE，读列表也保持一致读事务；业务值全部绑定。环境行与全部来源作为同一提交单位；失败回滚，确认提交后服务才返回成功。争写等待 2 秒；快照循环另设 5 秒截止。单值 1 MiB、SQL 64 KiB、最多 100000 条本地索引记录是资源防护预算，与商业免费 10 环境政策无关，写入前也检查预算，防止创建出下次无法打开的索引。

提交时 I/O 异常返回 outcomeUnknown，并封闭连接后续读写，要求重启核对。服务仍允许停止浏览器和撤销租约；不会因数据库故障剥夺这两项控制。没有自动重试写操作。

## 迁移和恢复

旧 `workbench-poc.json` 先整批校验 ID、名称、来源、代理及路径，再保留原字节的只读 `.pre-sqlite.bak` 副本，最后一次事务导入环境及导入标志。源 JSON 不再由新版更新，浏览器 ID、用户目录和会话文件不搬动。失败可重试；已导入时不重复导入残留的旧清单。禁止使用旧程序继续写同一根目录，避免出现两个格式各有新数据的分叉。

已有 v1 SQLite 在升级前通过 SQLite backup API 产生 `workbench.sqlite3.before-v2.<随机ID>.sqlite3`，再事务执行 ALTER TABLE、迁移记录和版本号更新；失败保留 v1。新建数据库从空库事务应用 v1/v2。SQL 校验和在源码审计时再次核对，不能悄悄改变已记录的迁移脚本。

`Catalog::Backup` 使用在线备份 API 生成自包含元数据快照，完成后验证并刷盘；拒绝覆盖任何已有目标。`Catalog::Restore` 先只读验证源，再复制至新文件并升级校验；失败清理本次新目标，不覆盖现有库。此 API 目前供核心层调用，未新增 UI/CLI/MCP 的备份按钮或命令。

这些是元数据层能力。浏览器 Cookie/站点数据、凭据、截图及流程不在该快照内；不得将它用于承诺完整环境迁移。加密包、DPAPI 可迁移密钥和跨机器恢复仍属于 T049/T055。数据库版本不通过反向 SQL 降级，恢复旧快照也只能写到新目标供独立核验。

## 验证边界

验收覆盖实际创建、服务自动导入、幂等、批量回滚、迁移及旧版快照、新文件恢复、只读及损坏拒绝、硬链接、并发及忙碌截止。独立子进程生成未提交 WAL 后直接退出，以及提交后直接退出，核对真正重开后的持久结果。

磁盘满与 fsync 回执异常使用仅编入测试目标的 SQLite 原生 VFS 注入，走实际 SQLite 事务路径；没有耗尽用户磁盘或声称模拟断电。断电、坏盘、网络盘和第二台干净 Windows 机器仍未验收。原有浏览器、代理和 MCP 的双配置回归必须同时通过，证据见 [T015 验收](../acceptance/T015_SQLite索引验收.md)。
