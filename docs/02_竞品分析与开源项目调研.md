# 比特浏览器与 ego lite 竞品分析及开源项目调研

调研日期：2026-11-03。文档版本：1.3。用途：为 AI 浏览器自动化工作台的功能设计与技术选型提供依据。

## 1 调研结论

两款产品适合组合的能力不同：比特浏览器提供面向多账号业务的环境管理体系，ego lite 提供面向 AI 的浏览器访问与任务运行体验。新产品的核心应当是“独立身份环境 + AI 任务空间 + 可调试流程”，并由同一套动作接口连接人工操作、流程引擎和外部 AI。

优先参考 `sheying2013/OpenBrowser` 的产品模块划分、`citrolabs/ego-lite` 的任务空间和语义操作设计，以及 Chrome DevTools MCP 的调试能力。自有程序按 C++14 实现；通过进程通信调用可独立升级的浏览器运行时。直接混合这些项目源码并不能得到可发布的 C++14 浏览器。

### 1.1 三个决定技术路线的事实

**ego lite 的 MIT 仓库不等于完整浏览器本体源码。** 官方 README 明确写道：“The contents of this repository are released under the MIT License. The ego lite browser is a separate, free download.” 仓库包含 TypeScript 运行时、插件、技能、原生接口契约和测试；本地运行文档要求先安装 Ego Lite，原生桥接仍由已安装的应用提供。[S09][S10]

**OpenBrowser 的应用许可与内核许可必须分别检查。** 其 README 声明应用为 MIT，同时说明 Windows x64、macOS arm64 官方构建使用 Wayfern 内核，并链接第三方服务条款；Ubuntu 使用 Chrome for Testing。不能把整个软件包一概视为 MIT 内核。[S13]

**现代 CEF 与 C++14 存在明确冲突。** 本次读取 CEF 主分支构建文件，Linux/macOS 设置 `-std=c++20`，Windows 设置 `/std:c++20`。因此，不能承诺当前 CEF C++ 包装层直接编译进 C++14 主程序。采用外部浏览器进程和 CDP 可把这一冲突隔离在边界之外。[S14]

## 3 比特浏览器分析

### 3.1 产品定位与主要特点

比特浏览器以多账号环境管理为中心。其官网列出指纹浏览器、多窗口同步、多账号管理、RPA、扩展中心、Local API、代理和团队管理。与普通浏览器的区别主要在于环境生命周期、批量操作和业务管理，而不仅是多开标签页。[S01]

| 能力 | 公开资料体现的内容 | 对新产品的价值 | 需要实际验证的部分 |
| --- | --- | --- | --- |
| 环境隔离 | 每个账号使用独立环境；支持分组、标签、批量管理 | 建立 Profile 管理中心 | 隔离覆盖哪些存储、进程及扩展状态 |
| 指纹配置 | UA、语言、时区、Canvas、WebGL、音频、字体、WebRTC 等 | 定义统一环境配置与检测报告 | 各内核、各系统的真实生效范围及一致性 |
| 独立代理 | 环境代理设置、连接检测、批量配置 | 每个身份环境保持独立网络设置 | SOCKS 认证、DNS、IPv6、WebRTC 的实际路径 |
| 窗口同步 | 主窗口操作同步到多个窗口；官网注明 Windows 支持 | 批量人工操作与演示 | 页面结构不同、缩放不同、弹窗时如何处理 |
| RPA | 拖拽流程、模板、定时执行 | 可视化流程及定时任务 | 运行并发、失败恢复、调试粒度与版本差异 |
| Local API | 环境、分组、标签等管理；接入自动化框架 | 兼容现有脚本、外部 AI | 鉴权字段、端口、返回协议和订阅限制 |
| 扩展中心 | 从商店或本地设置扩展，分配到指定窗口 | 扩展策略管理 | 第三方扩展许可、权限与自动更新影响 |
| 团队协作 | 成员、子账号、功能权限、环境共享 | 后续团队版 | 环境冲突锁、凭据传输、审计和云端边界 |

资料来源：[S02] 至 [S08]。不把官网“100% 无关联”“避免封禁”等宣传语作为可验证的工程保证。

### 3.2 适合借鉴的产品设计

1. 将环境当作持久化业务对象，拥有名称、分组、标签、代理、配置、运行状态和日志。
2. 提供批量创建、导入、启动、关闭、迁移与备份，减少重复设置。
3. 将代理、扩展和环境配置集中管理，使流程可以引用稳定的环境 ID。
4. 为手动用户提供窗口排列与同步，为开发者提供 Local API。
5. 明确成员权限与环境归属，避免团队共享等同于共享所有密码。

### 3.4 对 AI 自动化的不足与待补充能力

本次公开页面未能证明其具备与 ego lite 相同的原生 AI 任务空间、带引用的语义快照或统一 MCP 调试协议。不能由此断言它完全没有相关能力；这些应列为试用核验项。

新产品需要显式补充：AI 可读页面、元素唯一引用、基于角色和名称的定位、任务上下文、动作后验证、人工接管、执行预算、结构化错误、流程断点和证据回放。

比特官网 RPA FAQ 当前写明“1 个任务在执行，其余需要排队等待执行”。因此，多任务并行不能直接沿用其产品能力假设，应按本项目的资源调度设计独立实现。[S02]

### 3.4 源码与兼容边界

本次未找到可核验的比特浏览器完整官方内核源码。`YFCODER96/bitbrowser` 是第三方 TypeScript SDK，MIT 许可，提供窗口、指纹、代理和 Cookie 接口包装，不是比特浏览器本体。

可以实现独立的 BitBrowserAdapter：调用用户已安装客户端的 Local API，再把返回的调试连接交给受控自动化层。兼容性应限于明确列出的接口与版本，不能默认拥有该商业浏览器的分发、内核修改或云服务使用权。

## 4 ego lite 分析

### 4.1 产品定位与主要特点

ego lite 以人工与 AI 共用浏览器为中心。用户继续使用自己的区域，Agent 在独立 Space 中执行任务；通过 `ego-browser` 运行 JavaScript 工具调用，读页面快照并执行导航、点击、填写和等待。[S09]

| 能力 | 公开资料体现的内容 | 对新产品的价值 | 需要实际验证的部分 |
| --- | --- | --- | --- |
| 登录态复用 | 官网声明可以迁移 Chrome 数据并继承登录 | 用户登录一次，后续流程复用自己的环境 | 加密 Cookie、平台差异、需重新登录的站点 |
| 任务空间 | Agent 在自己的 Space 中运行；用户可查看或接管 | 人机协作、标签归属和并行任务 | 后台焦点、弹窗、键盘、文件选择的行为 |
| 代码式调用 | 一段 JS 组织多个动作，减少反复往返 | 批处理动作、流程封装、降低上下文开销 | 任务超时、取消、权限与部分成功恢复 |
| 语义快照 | 输出页面结构、可操作节点与引用 | AI 理解页面，减少依赖截图与长 CSS | 页面动态变化、复杂 iframe、Shadow DOM |
| 原生桥接 | 提供空间、标签、截图、CDP 等原生接口契约 | 设计统一 BrowserDriver 接口 | 已安装浏览器版本与运行时的配套关系 |
| 多 Agent 接入 | 面向多种可以调用工具或写代码的 Agent | 通过 MCP、CLI、API 对接外部 AI | 每个客户端的发现、鉴权与能力声明 |
| 本地存储 | 官网称浏览数据保存在本机 | 本地优先、减少不必要的数据上传 | AI 模型请求中发送了哪些页面内容 |
| 经验复用 | README 仍有 coming soon 描述，仓库已有 learning 目录 | 后续站点技能和可复用流程 | 已上线范围与宣传描述不完全同步 |

### 4.2 原生接口中值得借鉴的细节

原生文档定义了 `listProfiles`、`createTaskSpace`、`useTaskSpace`、`createTab`、`listTabs`、`snapshot` 等能力。Profile 决定任务空间使用的身份、Cookie、存储和登录态；空间归属与身份隔离是两个不同概念。[S11]

人工接管后，部分自动化调用会返回 `EGO_TASK_SPACE_USER_IN_CONTROL`。这体现了控制权必须是可验证状态，不能只在 UI 显示一个暂停图标。新产品需要让所有写入路径共享同一控制权门禁。

仓库中的 `native-gate.ts` 还明确处理进程级“当前选中任务空间”引发的异步串扰，使用队列覆盖整个原生操作。新产品应采用显式携带 profile、space、tab、frame、session 的请求，避免依赖可变的全局当前页面。

### 4.3 宣传能力与实际边界

官网强调跨域 iframe、Shadow DOM 和语义快照质量，但原生快照要求文档同时记录了 iframe 可操作节点缺失引用、节点 ID 在不同渲染器重复、稳定定位器必须校验唯一性等问题。[S12]

因此，不能把“跨 iframe 全部可操作”直接列为无条件复用能力。我们的验收必须覆盖 OOPIF、重复节点 ID、动态页面、不可访问的封闭组件，并允许返回明确的“不支持”或“引用失效”。

官方展示的速度、成功率和费用来自其自有 Real-World Bench。没有在本机复现，也没有跨模型对照，不能直接用这些数字估算本项目性能。新项目应建立固定任务集和基线。

### 4.4 开源范围与关键版本

- 仓库许可：MIT，覆盖仓库内容；浏览器本体另行下载。
- 运行时：TypeScript/JavaScript；公开 `package.json` 要求 Node.js 22 或更新版本。
- 核心原生桥接依赖已安装 Ego Lite；单独构建运行时不能独立得到浏览器。
- 实际平台：官方 README 当前列 Windows、macOS；Linux 仍在路线图。
- 本次取证提交：`12407167f84a58af24044f072868051952131491`。
- 主要复用方式：学习接口、状态机、测试场景；需要直接使用源码时，保留版权与许可并检查原生依赖。

## 5 两款产品的能力组合

| 设计维度 | 比特浏览器侧重 | ego lite 侧重 | 新产品方案 |
| --- | --- | --- | --- |
| 身份管理 | 独立环境、多账号、代理、指纹 | Profile 的登录态与用户日常浏览 | Profile 为身份边界，Space 为任务边界 |
| 操作入口 | 人工、同步、RPA、API | 外部 Agent 和代码式操作 | 人工、AI、流程调用同一动作服务 |
| 页面理解 | 自动化框架或业务流程 | 原生语义快照 | AX + DOM + frame 信息，必要时截图 |
| 并行策略 | 多环境管理；RPA 页面描述排队 | 多 Space 并行 | 资源队列 + 控制权租约 + 同身份写锁 |
| 流程生成 | 拖拽与模板 | Agent 编写代码和组合工具 | 自然语言生成草稿 + 可视化调整 + 录制 |
| 调试方式 | API 与现有框架 | 快照和工具调用 | 元素探查、Console、Network、断点、证据链 |
| 使用体验 | 批量账号运营 | AI 使用已登录浏览器 | 用户看得懂、能接管、流程可重复执行 |
| 可扩展性 | 扩展中心、团队能力 | Agent 技能与原生桥接 | 版本化动作插件、MCP、外部浏览器适配器 |

### 5.1 本次追加的 Web 功能测试需求

### 6.1 最值得继续做源码验证的三个方向

### 6.2 推荐组合

| 层次 | 基线选择 | 推荐原因 | 替换条件 |
| --- | --- | --- | --- |

## 7 不能仅凭设置界面判断实现成功的能力

1. 多窗口存在不代表 Cookie、IndexedDB、Service Worker、缓存、扩展存储互不混用。
2. 修改 `navigator` 的 JavaScript 返回值不代表 UA Client Hints、Worker、WebGL、字体等多层一致。
3. 配置 SOCKS5 不代表 DNS、UDP、WebRTC、IPv6 一定走代理。
4. Space 分开标签不代表身份隔离；同 Profile 通常共享部分状态和服务端账号。
5. 有 AI 对话框不代表具备可重复执行的自动化流程。
6. 录制到坐标不代表页面变化后仍能正确回放。
7. 能读 Network 不代表拥有站点所有业务 API 的稳定、授权调用方式。
8. 断线重连不代表可安全重试支付、发送、发布或删除等不可逆动作。
9. 快照里看见一个按钮不代表一定存在唯一、当前有效的节点引用。
10. 从 GitHub 下载成功不代表有权分发该项目引用的第三方浏览器内核。

关键补全决定：

- C++14 主程序可优先验证 nlohmann/json、draft-07 validator、date/tz、libsodium C API；Win32 传输备选 CivetWeb C API。Qt6 和 pixelmatch-cpp 当前要求 C++17，Tesseract 当前构建使用更高标准，采用 Qt5 路线或独立 Worker。
- nodeeditor 当前 CMake 有 Qt5 分支及 cxx_std_14 设置，可作为流程画布的具体验证候选；需要关闭默认 Qt6 并完成编译，不能仅看项目名判为不兼容。
- Mailpit/WireMock/Keycloak 提供受控测试服务，GOST 提供认证代理桥候选；缺组件时预检 blocked，普通登录测试不强制依赖全部服务。
- Pixelmatch、axe-core、Tesseract 分别补充视觉、无障碍和 OCR；rrweb 只补浏览证据，Playwright recorder 作为动作录制参考。所有动作仍经过本程序租约和权限层。
- WinSparkle C API 和 TUF 参考实现补签名更新/防降级设计；WebView2 COM 为独立嵌入 POC。WebView2Samples 的根许可入口尚未核实，暂不复制样例代码，可按 SDK 文档自研。

所有 F01–F65 已映射到边界和任务，见[文档 06](06_功能边界与源码补全方案.md)。其中专有浏览器本体、真实硬件身份验证和无可复现源码的高级内核，已明确替代/人工交接路线，不作完整兼容承诺。
